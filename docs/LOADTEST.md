# Навантажувальне тестування

Інструмент: [k6](https://k6.io). Сценарій: `loadtest/laptops.js`.

## Профіль «мало записів, багато читань»

Один віртуальний користувач (VU) у циклі виконує **1 запис і 9 читань**:

| Операція | К-сть за ітерацію | Запит |
|---|---|---|
| Запис | 1 | `POST /laptops` (створення ноутбука) |
| Читання списку | 4 | `GET /laptops` (найновіші 100, найважча операція) |
| Читання щойно створеного | 3 | `GET /laptops/{code}` |
| Читання випадкового недавнього | 2 | `GET /laptops/{id}` (200 або 404 допустимі) |

Між запитами пауза `THINK` = 0,2 с. У проєкті немає автора окремою сутністю (є лише ноутбуки), тому замість «даних автора» використано читання випадкового запису.

## Три фази

| Фаза | Тривалість | Користувачів |
|---|---|---|
| Наростання | 2,5 хв | 0 → N |
| Стале навантаження | 5 хв | N |
| Спад | 2 хв | N → 0 |

N підібрано так, щоб на сталому етапі CPU перевищував 60 % і спрацьовувало масштабування: **N = `__`** (⚠️ ЗАПОВНИТИ; пробуй 20, 30, 50).

## Запуск однією командою

```
k6 run -e BASE_URL=$(terraform -chdir=terraform output -raw app_url) --summary-export=loadtest/results/summary.json loadtest/laptops.js
```

Параметри: `PEAK_VUS`, `RAMP_UP`, `HOLD`, `RAMP_DOWN`, `THINK`, `NO_CACHE` (див. `loadtest/README.md`).

## Висновки
- Чому сценарій має фазу наростання: щоб не вдарити по холодному сервісу одразу (див. відповідь на питання 8 нижче) і побачити момент перетину порогу.
- *(1–2 речення власних спостережень: на якій хвилині спрацювало масштабування, чи були 5xx, як змінилась p95.)*

## Відповіді на питання
- **Чому наростання, а не миттєвий старт N користувачів?** Холодний сервіс (1 екземпляр, порожні пули) від миттєвого шоку дає шквал помилок і таймаутів, які не відображають реальну поведінку, а політика масштабування отримує спотворену картину. Поступове наростання показує, при якому навантаженні сервіс починає «здавати», і дає автомасштабуванню час відреагувати.
- **p50/p95/p99:** 50 %, 95 %, 99 % запитів були швидшими за це значення. Середнє приховує «хвіст»: сервіс із avg 80 мс може віддавати кожен 20-й запит за 2 с. Користувач відчуває саме повільні запити, тому дивимось p95/p99.
- **RPS проти одночасних користувачів:** пов'язані через латентність: RPS ≈ VU / (латентність + пауза). Чим повільніший сервіс, тим менше запитів/с видає той самий набір користувачів.
